## Folders (3 October 2026; called Files until 7 October)

- **An app of its own** (11 October 2026: "we should keep Folders as an independent, separate app. Maybe we can offer it as separate app in the future"). Folders needs nothing but the toolkit and the shared code beside it to run: not the ring, not Trindle's compositor, not another Trindle program. What reaches outside it (pinning to the ring, snapshots for earlier versions, opening Settings or Drives) is looked for when Folders runs and is left out, or greyed with a plain reason, where that part is not there.
  - **What it needs to run, and nothing more** (audited 11 October 2026, so that it could be packaged alone later; the packaging is not built).
    - The Trindle Toolkit (`crates/trindle-toolkit`, a library of its own) and the shared code (`src/common`), which would ship with it, and with them the style sheet (`share/style.css`), the Trindle Sans font and the icon set its icons are named from.
    - A Wayland compositor with the ordinary window protocol. Its window is a plain window: it asks for nothing that only Trindle's compositor has.
    - The person's own Trindle settings folder, where it keeps its pins, colours, views, columns and widths, and its own settings (`folders.conf`: where it starts, file endings, tick boxes, opening drives; see Its own settings). Every one has its usual answer when the file is not there. Beside it, `hidden-drives.conf`, the drives and parts the person has hidden (see Drives, Hiding a drive); with no such file nothing is hidden.
    - Itself, started again under its other names for work it boxes or hands on: the unpacker and the thumbnailer inside bubblewrap, the helper that asks for a server's password (`trindle-askpass`), a new window, and a window as administrator. A package of Folders alone carries those names.
  - **What it uses when it is there, and does without when it is not.** Each is looked for when Folders opens and each time its window has the keyboard again, or when it is first needed, never taken as there because Trindle was built with it (`src/files/alone.rs`). A row that needs a missing part is not in any menu, and the groups of the menu keep their room.
    - **The ring.** "Pin to the ring" is offered when the ring's favourites file or its program is there (see Pin to the ring). Without: no row.
    - **Trindle's wallpaper program** (`trindle-wallpaper`, or the one program that holds every part). Without: no "Set as wallpaper".
    - **pkexec**, polkit's own. Without: no "Open as administrator".
    - **A terminal**, any installed. Without: no "Open in a terminal", and F4 says "No terminal is installed to open this folder in."
    - **Trindle's helper** (`trindle-admin`), which sets sharing up and mounts Windows shares. Without: no "Share on the network"; a folder's Properties keeps its Share part, greyed, saying "Sharing a folder is set up by Trindle's own helper, which is not on this computer." (a folder shared already can still be stopped); and opening a Windows share says "Opening a Windows share needs Trindle's own helper, which is not on this computer." A computer's shares are still listed, by smbclient.
    - **trindle-wsdd**, which finds Windows computers. Without: Network still finds the computers that announce themselves by multicast DNS, which Folders asks for itself, lists what is mounted and what is typed, and when nothing is found says in plain words that the Windows way could not be asked and why. (Until 11 October 2026 it said nothing.)
    - **The session bus.** With it, a second start hands its folders to the Folders already running, under Folders' own name (`org.trindle.Files`). It also answers `org.freedesktop.FileManager1` (see "Show in folder" below). Without: each start is a window of its own.
    - **UDisks on the system bus**, for the Drives part of the sidebar; **a keyring** speaking the Secret Service, Trindle's or any other, for remembered passwords; **bubblewrap, ffmpeg, pdftoppm, libarchive, pw-play, smbclient, mount.cifs, ssh, fc-cache, and xdg-open**, each as said where it is used. Without any of them that one thing is not offered or says so in plain words, and the rest works.
    - **The compositor's idle notice** (ext-idle-notify), for the indexer, which goes by how busy the computer is without it; **a clipboard other programs can read** (the data-control protocol), without which Cut, Copy and Paste still work inside Folders.
    - **Home snapshots** and **the Drives code**, for Earlier versions and Storage: see those.
  - **Its own settings** (11 October 2026: "put the settings not in the settings app but here in the folder, so remove them from settings and put them there... we could have it as a standalone app that other distros may want to use, so having the settings in settings makes no sense"). Folders' options are in Folders, and Settings has no page for it.
    - **Where.** A round cog at the far end of the top bar ("Folders settings (Ctrl+comma)" as its tip) and Ctrl and comma open a card laid over the Folders window, like Properties: "Folders settings", with a strip of three parts, each a page of its own, closed by its cross or Escape. It is not a program of its own and not a system window. `trindle-folders --settings` opens Folders at the card, or asks the Folders already running to show it (the `Settings` call of `org.trindle.Files`).
    - **Every option the Settings page had, in the same words; none was dropped.** When Folders opens: one sentence saying how it opens now, the three answers as radio buttons (Home and Recent; Where each pane was left; Places set here), then Left pane and Right pane, each a list of the usual places (Recent, Home, Documents, Downloads, Pictures, Trash) with a round button, Choose another folder, which opens the file chooser; the two are greyed unless the answer is Places set here. The list: Rows (new that day, see Density below), then Tick boxes for picking and Show file endings, each a switch. Drives: Open drives when plugged in, a switch. The small picture of two panes the Settings page had is not on the card.
    - **Kept logins** (15 October 2026), a fourth part of Folders settings: each computer a login is kept for, with the user names kept for it and how many of its 90 days are left ("80 days left", "Less than a day left", or "Asks again at the next opening" when none is), and a red Forget button that lets go of the login and the addresses kept with it for good. The keyring is asked, with its deadline, each time the part is opened and again after a Forget; one that is locked or silent is said in red, never shown as none kept; a Forget that fails says why in red under the list. Tested: `kept_logins_are_listed_with_time_left_and_forgotten_by_a_red_button`.
    - **Kept as it is changed.** There is no Save button. A change is written at once; the line's box glows where it has one, and a switch or a choice shows its own answer, by the same rule as Settings' lines. A change that could not be written says "It could not be saved." in red under its line, and the control stays as it was. Tick boxes and file endings show in the list behind the card at once; where it starts counts from the next time Folders opens. **A file that cannot be read is never written over** (12 October 2026, from the code review of that day; until then it was taken for an empty one, and the next change wrote it out with that one setting and lost the rest). A settings file not made yet is simply empty; one that is there and cannot be read, is not text, or is over a megabyte is an error (`common::files::read_small`), and the one writer of such files (`update_env`) then writes nothing. The card says so in red at its top, on every page: "Folders' settings could not be read, so the usual answers are shown, and nothing here can be changed until they can be: the file that keeps it is not text and cannot be read." and under the line that was tried: "It could not be saved. Nothing was changed, because the file that keeps it is not text and cannot be read." A value with a line break or any other unprintable character in it is refused the same way, as it would write a setting of its own. The same holds for every file kept this way, Trindle's own settings file among them, and for the list of hidden drives. **And every other file Folders writes out whole** is held to it (found by an audit the same day): its pins, colours, views, groups and column widths, the list of recent files it shares with other apps, and the certificates a person has trusted for a server. Each is written from what was read of it, so one that is there and cannot be read is left exactly as it is (`common::files::may_rewrite`, `read_within`), and the change says it could not be kept; a certificate that cannot be remembered is simply asked about again. Tested: `a_file_that_cannot_be_read_is_an_error_and_is_never_rewritten`, `a_value_that_would_not_stay_on_its_line_is_refused`, `a_file_that_may_be_written_and_not_read_is_not_written_over` and `a_log_that_cannot_be_read_is_left_alone` in `crates/trindle-toolkit/src/common/files.rs`; `a_file_that_cannot_be_read_keeps_every_setting_and_a_line_break_is_refused` in `src/common/folders_conf.rs`; `settings_that_cannot_be_read_are_said_in_red_and_never_written_over` in `src/files/settings.rs`; `a_kept_file_that_cannot_be_read_is_never_written_over` in `src/files/kept.rs`; `pins_and_recent_files_that_cannot_be_read_are_never_written_over` in `src/files/places.rs`; `a_list_of_certificates_that_cannot_be_read_is_never_written_over` in `src/files/remote/tls.rs`; and `a_list_that_cannot_be_read_is_never_written_over` in `src/common/hidden_drives.rs`. **Written as a new file, never over the old one** (12 October 2026, from the third review of that day). **The fault:** the column widths, the preview panel's and the columns' files, the icon size, the pins and where the panes were left were written over where they lay, so a crash or a full drive part way left half a file or an empty one and the old words were gone; the one shared writer did go by way of a spare file, but one with a name anyone could guess, shared by every file of the same first name, opened through whatever lay under that name (a link left there had the new words written through it to wherever it led), and never written out to the drive before it took the old file's place. **The rule:** every small settings file is written by one writer (`common::files::write_whole`, which `write_text` and `update_env` use): the new words go into a new file beside the old, under a spare name of its own that is made new and never opened through anything already there, are written out to the drive (`sync_all`), and only then take the old file's place in one step, after which the folder's own note of it is written out too. At every moment the name leads to the whole old file or the whole new one; a write that fails leaves the old file as it was and removes the spare one, and the change says it could not be kept. A settings file that is a link stays a link, and the new file may be read by whoever could read the old. Folders' own kept files, its pins, the recent list and the trusted certificates all go through it. **The rest of Trindle writes the same way** (12 October 2026, later the same day; those still writing in place outside Folders, found by that audit, had been left to their owners). The rule for every part: a file that holds a person's choice or their work, or that the computer reads at its next start, and that cannot be made again from something still on the computer, is put in place whole by the one shared writer; a file no one else may read goes through its private kin (`write_whole_private`: the new file is for this person alone, 0600, from the moment it is made, whatever the old one was). Moved onto it: the hash of the PIN, and the clipboard's list (both private); the launchers in autostart, when one is added, delayed or switched; which program opens which kind of file (`mimeapps.list`); the Flatpak overrides put back from a backup; Apps' kept answers from the code hosts; the compositor's note of Num Lock and its list of keyboards and mice seen before; the colours the dropper kept; the folder each program last chose in, in the file chooser; a person's picture for other programs (`~/.face`); a screenshot saved under a name the person chose, which may be one that is taken; the settings put back when the assistant's change is undone, which were copied over the settings file where it lay; the login screen's notes of who logged in last, the screen reader and the plain drawing; the start-up times saved to Downloads; the crash reports' settings; the files the keyring's move writes; and the administrator's list of snapshots still to remove. What still writes some other way is counted file by file in `src/common/no_writing_in_place.rs`, each with its reason: those that are whole already by a spare file and a rename of their own, for a need the shared writer does not have (the keyring, root's helper, the lists another part reads while they change); marks, locks and notes for this session, which are empty or a word and made again at every start; the kernel's own switches in /sys; what is made again from something still there (thumbnails, drawn icons, copies of a font or sound the person still has, a file fetched to look at); new files in a folder made for the purpose and thrown away whole if the work stops (a backup being put together, an app's box, the new system during an install); and Text's cases named under Saving never loses the old words. **What the sixth review found in it** (12 October 2026). W-H1: the list called every copy of a file the person still has safe, and a sound added in Settings was copied straight onto whatever had its name in the person's sounds, so a sound of their own with that name was gone. A file a person chooses (a sound, a font, a picture) is now copied into a folder of theirs in one way, `common::files::copy_in`: the copy is made whole under a spare name and nothing there is ever written over; when the name is taken by a file holding the very same bytes that is the copy and no more is made, and when it is taken by anything else nothing is copied and the two are handed back (`Put::Taken`), to be asked about (see **Same name: asked, never a second name** below). A copy to a name that must be free is `copy_new`, which refuses a name that is taken, and one over a file that is to be replaced is `copy_whole`, whole in one step, which `copies::replace` uses for the answer yes. W-M1: the scan saw only four ways of writing a file where it lies. It now also counts a file opened to be written with nothing made new, one added to at its end and one given a new length, and in a second list, file by file, every place that removes a thing or renames one by a plain rename, which goes over whatever has the name: a new one fails `nothing_is_taken_away_or_named_anew_but_where_it_is_counted` until it has been looked at and counted. Tested also: `a_file_copied_into_a_folder_never_writes_over_what_has_its_name` in `crates/trindle-toolkit/src/common/files.rs`. Tested: `nothing_is_written_over_where_it_lies_but_what_is_listed`, which reads the whole source and fails on any new place that writes a file where it lies until it uses the shared writer or is listed with its reason; `a_private_file_is_put_in_place_whole_and_for_this_person_alone` in `crates/trindle-toolkit/src/common/files.rs`; and, with the drive made to fill half way, `a_launcher_is_whole_as_it_was_when_a_change_cannot_be_written` (`src/common/autostart.rs`), `the_list_kept_is_whole_as_it_was_when_it_cannot_be_written` (`src/compose/newcomers.rs`), `a_picture_replaced_is_whole_as_it_was_when_the_new_one_cannot_be_written` (`src/screenshot/mod.rs`) and `the_folders_last_chosen_in_are_whole_as_they_were_when_they_cannot_be_written` (`src/screenshot/file_chooser.rs`). **Lines it does not understand are kept** (the same day). **The fault:** a line a newer build had written, a line with no tab or a word that is not text was dropped from the colours, views, groups and widths the next time anything in the same file changed. Trindle's own file manager, on the Trindle Toolkit, with the same bubble-wrap look as every Trindle part. It is the only file manager Trindle installs. Mouse first, with keyboard shortcuts for everything.

- **Name** (7 October 2026). It is called Folders, not Files, because Files is what GNOME calls its file manager. Every word a person sees or hears says Folders: the window title, the launcher, the ring, Settings, Help, the Welcome, notices and the screen reader. The command is `trindle-folders`; the command `trindle-files` still starts it, so a link or a shortcut made before still works. The old launcher `trindle-files.desktop` is no longer installed (10 October 2026; nor is Apps' old `trindle-store.desktop`): a favourite saved under an old launcher's name is written back under the new one once, and a default for folders chosen before falls to Folders, which `trindle-mimeapps.list` names for `inode/directory`. Saying "open files" aloud still opens it, and typing "files" in All apps still finds it, by its keywords. The window's id, the D-Bus name `org.trindle.Files` and the Rust module `src/files` stay as they are inside; both names are in `apps::OWN`. "Files" meaning ordinary files (a file, files in a folder, copy files) is unchanged.

  - **Why a copy made a computer slow, and what is done about each cause.** (a) *Unwritten data.* A fast source and a slow drive fill memory with data not yet written, and everything then waits while it is. Folders writes in steps of 8 MiB and has the kernel write each step out as it goes (`sync_file_range`, or `fdatasync` on a kind of file that cannot be asked that way), waiting for the step before, so no more than two steps of one file are ever waiting; small files, which never fill a step, wait together, never more than 32 MiB or 64 files of them. (b) *The kernel's store of files read.* A big copy would push every other program's files out of memory. What has been written out is given back at once (`posix_fadvise` DONTNEED); the source is read as one straight run (SEQUENTIAL) and each step of it is given back once read, but only if none of it was in memory before it was read here (`cachestat`), so what another program was using stays. Where the kernel will not say (an older kernel, or a file that is another person's) the step is given back; pages a program has mapped are never taken by that. (c) *The disk's queue.* The threads that do the work are in the idle class for the disk (`ioprio_set`). That is kept to by the BFQ scheduler only (and the old CFQ); with mq-deadline, kyber or none, which most NVMe drives use, it does nothing, so it is never relied on alone: (a) is what bounds the harm there. (d) *The processor.* Those threads, and the outside programs that do such work (tar, rsync, cp), run at the lowest priority (nice 19), for those threads only and never the one that draws a window. (e) *Memory.* A buffer is 1 MiB; four files at once can hold at most 4 x (1 MiB + 16 MiB) + 32 MiB = 100 MiB, nearly all of it data on its way to the drive, not Folders' own. (f) *The window.* Nothing on Folders' own loop waits on the disk or the network during a copy: the work is on threads of its own and sends word. (g) *The other end.* What is in flight to a server is bounded across all the files going at once: 64 SFTP requests of 32 KiB, 2 MiB in all, shared out among them (32 each for one or two files, 21 for three, 16 for four), with one sign-in. No setting is added: a copy on a computer that is doing nothing else runs at very nearly full speed.

When Folders on the receiving computer is the one doing the copy (fetching from the other), all of (a) to (f) hold there, since the writing is then Folders' own.

- **Archives** (10 October 2026: "Yes, teach Folders rar and remove File Roller"). Folders opens every kind of archive a person is likely to meet, and no other archive program is installed. A double click opens one like a folder, to look inside and take out chosen things; Extract here and Extract to a folder unpack the whole. All three show how far they have got, can be stopped, and say a failure in plain red words with its reason after the archive's name. Folders makes .zip and tar (plain, or squeezed with gzip, bzip2 or xz) and nothing else: nobody needs to make a .rar.
  - **Read by Trindle's own Rust:** zip (stored and deflated, Deflate64 as Windows makes of files over 2 GB through the deflate64 crate, ZIP64), 7z (LZMA, LZMA2, stored, the x86 and delta filters), tar plain or squeezed with gzip, bzip2 or xz, and a file squeezed on its own with gzip, bzip2 or xz, which opens as an archive of that one file, named as the archive is without its ending.
  - **A 7z's header is a stranger's too.** A count of files the rest of the header cannot hold (each needs a name of at least two bytes) is refused before any room is made for it, so a few bytes cannot ask for a gigabyte; the empty files are counted once, not for every property; and the dictionaries of the coders in one block may take 2 GiB together, not each (real archives chain one compressor and a filter). Tests: `a_7z_that_counts_more_files_than_its_header_holds_is_refused_and_a_full_one_opens`, `a_7z_block_whose_dictionaries_together_are_too_big_is_refused`.
  - **Read by the system's libarchive** (Debian's libarchive13t64, BSD licence, already on every Trindle computer because Flatpak needs it): RAR 4 and RAR 5, whole or split across files (name.part1.rar and on, or name.rar, name.r00 and on, found beside whichever part is opened and all shown to the box), disc images (.iso), CAB, cpio, RPM, ar and .deb, LHA, XAR, tar and lone files squeezed with zstd, lz4, lzma, lzip or compress, and any zip or 7z packed a way the readers above do not know (bzip2, PPMd and the like). Every one of these kinds has a test that lists and unpacks it through the box; where no program on the build computer writes a kind (CAB, LHA, XAR, RPM, lz4, lzip, compress), the test writes one from the format's own description, really squeezed. This is the one part of reading archives that is not Rust. No Rust reader of RAR could be used: unrar's code and everything made from it carries a licence that restricts use, which the GPL does not allow, and the one free Rust reader, rars (Apache 2.0, first published in May 2026), needs Rust 1.87 where Debian 13 has 1.85. Look again when Debian's Rust allows it. Nobody writes a RAR decoder for Trindle.
  - **The box.** libarchive is C reading a stranger's file, so it never runs inside Folders. Folders starts itself again as `trindle unarchive` inside the bubblewrap box the thumbnails use: no network, no D-Bus, no home, nothing it can write to, only the one archive and that read only, 2 GB of address space, and two minutes of processor time to say what is in an archive or two hours to unpack one. The child writes what it finds to its output as plain frames (a thing's name, kind, permissions, date and size, then its bytes), and Folders checks every length in them and puts what comes out through the same unpacking as a zip. A child that has been taken over can only send frames. The library is looked for when it is first needed, not when Trindle is built; without it, or without bubblewrap, these kinds say so in plain words and the rest still open. libarchive's mtree, a list that can name other files on the disk, is not turned on.
  - **The rules, the same for every kind,** kept in one place (`archive::unpack_in`) and each with a test. Nothing is written outside the folder asked for: a name with `..` in it or starting at `/` is refused and listed; links are made last, so nothing is ever written through one, and a link that points out is refused. Devices, pipes and sockets are never made. Owners are never brought back, and the set-user, set-group and sticky bits are dropped. No more than a million things, and no more bytes than the disk has free less 256 MB, come out of one archive, so one made to fill a disk or bury a folder is stopped, each with a plain message. Names with odd characters come out as they are, and bytes that are not UTF-8 come out as the mark for a letter that could not be read. Everything is unpacked in a hidden folder beside where it is going and moved into place only when it is whole, so a damaged archive, a failure or a stop leaves nothing behind. Nothing that comes out is ever run.

  - **Passwords** (10 October 2026). A zip or 7z locked with a password is unlocked by Trindle's own Rust once the person has typed it: zip's first lock (ZipCrypto) and WinZip's AES at each of its three strengths, and 7z's AES-256, whether only the files are locked or the names too. Folders asks in a card laid over its own window, as its other questions are, never a window of the system's: the archive's name, a box that shows dots with the toolkit's eye in it, as every password box has (11 October 2026), and the one action, Open or Extract. Where only the files are locked the archive still opens to look inside with no password, and what is not locked in it comes out without one; where the names are locked too it asks before it lists anything, and for anything taken out of it after. A wrong password is said in red under the box, "That password does not open it" (or, for a 7z with its names in the open, which keeps no check of the password itself, "That password does not open it, or the archive is damaged"), and the card stays as it was, the same size, with what was typed, for another try. Escape closes it and leaves nothing behind: nothing is unpacked, and a pane that was showing the archive goes back to the folder it is in. Locked archives extracted together are asked about one at a time. With another window of Folders in the way there is nowhere to ask, so it says "it is locked with a password" in red, and extracting it again asks.
  - **Where the password is.** Only in memory: on the card, in the thread that tries it, and in the work that needs it, each copy wiped as that ends (the zeroize crate, which the AES keys made from it are wiped by too). One more copy is kept, in memory only, while a pane (in front or in a tab behind) still shows the inside of that archive, so the person is asked once and not again for each file opened, viewed or taken out (10 October 2026: "Yes, remember the password while the archive is open"). It is wiped as soon as no pane shows the archive, when the archive's file changes, when a use of it shows it no longer fits, and when Folders closes; an archive extracted without being opened keeps nothing. The card says so under its box: "Kept only while this archive is open, never saved." It is never written to disk, never logged or printed (the type that holds it cannot be printed), never on a command line or in the environment, and never handed to the box: libarchive is given no password at all. What is unlocked to be shown in the viewer is removed when the viewer closes, and what is unlocked to be opened in its own app is removed when Folders closes, or at its next start if it was stopped short.
  - **What stays locked.** A RAR locked with a password, which libarchive 3.7.4 cannot unlock: it says "it is a RAR locked with a password, which Folders cannot unlock; nothing is wrong with the file". A zip or 7z that is locked and also packed a way the readers here do not know (PPMd, BCJ2, bzip2 and the like, or PKWARE's own "strong" lock): it says "it is locked with a password and packed a way Folders cannot unlock". Neither asks for a password that could not help. The ciphers are the aes, sha2 and ring crates the build already had; nothing was added. Once unlocked, a locked archive comes out through the same `unpack_in`, held to every rule above, each tried on a locked archive made to do harm. Folders reads a RAR's headers itself before unpacking (it follows them and unpacks nothing), because Debian 13's libarchive (3.7.4) hands a locked RAR 5 file back still scrambled, takes a RAR 5 cut off between two files for a whole one, and with a part of a split RAR 5 missing gives the start of a file as if it were all of it. The same libarchive ends every file of a XAR but the first with noughts, as many as the files before it were long, so the child sends no more of any file than the archive says it holds. A split RAR with a part missing says "a part of it is missing, and every part has to be in the same folder".
  - **Opening.** Folders is the default for every archive type in `trindle-mimeapps.list`, its launcher lists the same types (a test keeps the two in step), and `trindle-folders some.rar` opens the archive like a folder. A .deb stays with the installer on a double click; Extract still unpacks it.

The speed is measured once a second and smoothed (three parts in ten of each new measure), so one quick or slow second does not show and the words change no more than once a second; the time left counts down steadily and takes a new guess only when it differs from the count by more than a fifth. It is said no finer than it can be trusted: "a few seconds left", "about 20 seconds left", "about a minute left", "about 2 minutes left", "about 3 hours left". Until two measures are in, and whenever the work stands still, the card says "working out how long…" and promises nothing. A copy of 50 files or more counts them too: "1,240 of 9,000 files, 24 MB a second, about 2 minutes left". Work that goes a thing at a time (the Trash, deleting, pictures) says "20 items a second". A paused card says "paused" and one with a question "waiting for an answer"; time spent paused or waiting is not counted as going slowly. The words are one line whatever they say, so the line never changes height.

    - **A move takes away only what it has seen arrive** (12 October 2026, from the third review of that day). **The fault:** a move to another drive is a copy and then the first taken away, and the first was taken away as one whole folder by its name. A folder inside it that could not be read was said to have failed, and then went with the rest: what was in it was never copied and was removed for good, not even to the Trash. Anything put into the folder while the copy ran went the same way. **The rule, in one sentence:** a thing is taken from where it was only when that very thing is known to have been copied whole and checked, and a folder only when it is then empty. How (`Moved` and `leave` in the toolkit's `src/common/file_work/work`):
      - **Each file is checked as it is copied.** The copy is written out to the drive before it counts (`sync_all`), its size must be the size that was read, the first file must be the same size and age when the copy ends as when it began, and a file of up to a megabyte is read back and compared with what was read. Anything else is a copy that failed: the copy is removed and the first stays.
      - **Nothing is removed by a folder's name.** Each thing that was copied is removed alone, from the opened folder it is in, and only if it is still the very thing that was copied (the same thing on the disk, the same size, the same age). A folder is read again when its turn comes: anything in it that was not copied, that came since, that changed since, or that cannot be read stays, and so does the folder, which is removed only once it is empty and by a call that cannot remove a folder with anything in it.
      - **A folder that cannot be read whole is not gone into at all for removing.** A folder that could not be listed, or whose list stopped part way with an error, is copied as far as it could be read and nothing of it is taken away.
      - **It says what happened.** The card's red words name each thing that stayed and why, and for a folder moved in part say so: "Holiday (moved in part: 2 things in it could not be moved and are still where they were)". Undo moves back what did arrive.

    - **Five rules, each said once** (12 October 2026, from the fourth review of that day). Four reviews in one day each found a neighbour of the fault the one before had mended, which is what mending case by case does. So each rule is said here once, is written again at the top of the code that keeps it, and that code is made unable to break it: what removes, sends or trusts takes a value that only the check itself can make. The paragraphs elsewhere in this document tell how each came about; where one of them and this differ, this is the rule.
      - **Removal.** Nothing of the person's is removed, put in the Trash or written over, on this computer or on a server, unless that very thing is proved to have been copied whole, or the person asked for it to go. That very thing is known by what it is and never by its name: on this computer the disk and its number there, with its length and its times (`proof::Seal`); on a server its length and the time the server gives it, asked of the server afresh just before, since no server gives a number that cannot pass to another thing. A thing that cannot be listed, read or told apart is left where it is, and named in the red words. A folder on a server is asked to be removed only when every thing in it was itself seen to go, and a list asked for just before shows nothing in it of any kind, readable or not: WebDAV removes a folder with all that is in it, so no server is trusted to refuse. A folder here is removed only by the call that cannot remove one with anything in it. **How the code is held to it** (the toolkit's `src/common/file_work/proof.rs`): the proof of a copy is a value, `proof::Copied`, that only the checks which prove a copy can make (the first unchanged from its first byte to its last, every byte of it read, and the copy that long where it lies), and each function that takes a first away asks for one: `proof::take_away` on this computer, `Go::remove_first` in `src/files/far.rs` for either end of work with a server. On this computer the thing is first given a name of the move's own in the same folder, looked at again under that name, and only then removed; when it is not the thing that was copied it is given its name back and stays (F-3: before, it was looked at by its name and then removed by its name, and what took the name in between was removed, never having been copied). **Doubts raised in other files, each looked at** (task 310 item 45, 18 October 2026): a restore of an app's data sets the folder that was there aside and removes it only once the backup's is in place, giving it back if the restore fails (`store/flat.rs`); a backup is written under a spare name beside the place chosen and swapped in only when whole, so a failed one never takes away a good backup of the same name (`store/backup.rs`); putting an earlier version back uses the rename that refuses a taken name for both of its renames (`common/earlier.rs`); `trindle-wsdd --listen` removes the old path only if it is a socket (`session/wsdd.rs`); a plugin's update sets the old program aside until the new one is in its place and gives it back if the swap fails (`plugins/mod.rs`); the face picture the account portal reads is read from the file as opened, a plain file of at most 16 MB, never a pipe waited on (`screenshot/portal_access.rs`). Each has a test or sits under an existing one. **Arming is the person's too** (task 310 item 47): on Settings' Power page the first press of Log out, Suspend, Restart and Shut down, which only arms, must be the person's own as the second is (`Node::own_act`, `widget::remove_by_hand`, `settings::ui::confirm_by_hand`); a made-up press arms nothing, stands an armed one down, and the label says why where it was pressed. Permissions and Install are held by tests that press them (item 48), not only by a source check of their guard lines. **Not decided, asked of the owner** (item 49): putting a backup back in Apps (it ends the running app), turning a plugin off or removing it, and turning the screen reader off end a program and are not on the list of acts only the person may do; recommended, all three the person's alone except the screen reader, which a blind person must be able to switch by its own key. **Wipe inside a folder** (task 310 item 44, 18 October 2026): the window offers Wipe for files only, and Wipe is not to be offered for a folder until the work keeps this rule. It does now (`wipe_one` in `src/files/wipe.rs`): the folder asked about is opened and must be the very folder the person was asked about, each thing in it is reached by one name within a folder held open, following no link (the way Delete for good empties a folder), and a folder inside swapped for a link to somewhere else meanwhile sends the work nowhere; a test swaps one in the moment after the folder was listed. The thing a person was asked about replacing is the one that goes to the Trash: what took its name while the question was up was never asked about, and stays. **What the fourth review found, and what each was.** F-1: a WebDAV folder whose only child the server named and would say nothing more of (a 403 for its properties) read as empty and was removed, child and all; such a thing is now listed, as a thing that is neither file nor folder, which nothing copies and which keeps its folder. F-5: a copy to a server that failed removed whatever then had its name; now only the spare name of its own making. F-8: an archive whose spare name could not be removed was said to have failed though it lay whole under its name, and Undo knew nothing of it; once it has its name it is made. And three found by holding the rest to the rule: a file moved from this computer to a server was removed here if the name still led to a file of the same length, though another program had put a new file there meanwhile; a folder moved from a server was removed there though another person had put something in it since it was listed; and a file whose first could not be removed still counted as moved, so the folder round it was asked to be removed. **Deleting for good goes by the thing that was asked about** (13 October 2026, the seventh review, F-M2). **The fault:** Delete took a thing away by its name alone, looked at once as the work began, so whatever had the name by then went, a folder with all beneath it: another program of the same person had only to put a folder under the name after the person said yes. Asking is the other half of the rule, and the answer is for the thing that was asked about. What has the name is opened within its folder, following no link, and must be that very thing. A folder is then emptied through what was opened: each thing in it is opened by its one name within the opened folder and removed by that name within it, at every depth and never by a path, and the folder's own name is removed by the call that cannot remove a folder with anything in it. A file or a link is given a name of the work's own, looked at under it, and removed only if it is the thing asked about; anything else is given its name back. A thing with no proof, or that is another thing by now, stays and is named: "it was not there when this was looked at, so it was left". The same holds for emptying the Trash, and for a thing on this computer deleted along with things on a server. **Wipe securely** is held to the same: only the very files the person was asked about are written over, and each name is removed only once what it led to has been looked at under a name of the wipe's own; a file that is another by then is left ("it changed meanwhile"). It is left under its own name; when another program has taken that name in the same moment it is given the nearest free one ("report (2).txt", by the rule a move's first is given its name back by, `proof::named_back`), never left under the wipe's own meaningless name, and the wipe names it by where it lies.       - **Overwriting.** Nothing is written over a name that something else made meanwhile. On this computer a new thing is made by a call that fails when the name is taken (`O_EXCL`), and a thing is given a name by a rename the kernel refuses when the name is taken (`common::files::rename_new`); where a drive cannot be asked to refuse (F-2: NFS and some others answer that they do not know the question, and the name was then looked at and taken, so a file another computer made in between was written over), a second name is made for a file, which fails when the name is taken, and the first name then removed; and for a folder an empty folder is made under the name, which fails when it is taken, and the folder then takes that empty one's place. On a server a file goes under a spare name nobody else would choose (its own name, eight random bytes and `.trindle-part`), made new where the server can refuse a name that is taken, and is then given its name by a rename the server refuses when the name is taken. **What each kind of server can promise.** SFTP: both (an exclusive open; a rename that fails on a name that is there). WebDAV: both (`If-None-Match: *` on the PUT, which a server that honours it refuses, and `Overwrite: F` on the MOVE, which the standard obliges every server to refuse with 412); a server that ignores the first still writes over nothing, as the spare name is nobody else's. A phone (MTP): it has one session, Folders', and Folders looks first. **FTP cannot promise it:** it has no way to refuse a taken name, for a new file or for a rename. Folders sends under the spare name, looks for the name just before the rename, and says so where the person connects: the Connect card for an FTP address has the line "This server may give two files one name." (plain words, 15 October 2026) A file that takes the place of one already there, at the person's word, still comes beside it first and takes its place whole. **Spare files are private from the moment they are made** (F-7: a settings file's spare was made as any new file is and only then given the old file's mode, so for a moment a private file's new words could be read by others): made for this person alone (0600) and given the old file's mode, or the mode any new file has, only once it is written. A spare file is never opened through a name left in the way: it is made new, and when the name is taken another is tried. The spare file for bytes on their way between two servers is made the same way, where it was opened under a name that could be guessed. **A settings file that is a link** is written through to where it leads, link after link, and stays a link (F-6: a link to a file not there yet was replaced by a plain file). When the folder it leads to is not there, or the links lead round, the write is refused in words, "it is a link to a place that is not there", and nothing is made up. **Taking a place on a server** (13 October 2026, the seventh review, F-M1, and F-M6 of the sixth). **The faults:** where a server refuses a taken name the old file was removed for good and the new one then given the name, so when that second step failed the old one was lost, and a server has no Trash to find it in; and on FTP the new one was renamed straight over whatever had the name a moment after it was looked at, so what another person saved there in that moment, which nobody was asked about, was written over. **Now, on every kind of server:** the old one is given a spare name of the work's own beside it (a rename takes whatever has the name at that very moment and nothing after), looked at under that name, and must be the thing the person was asked about, or it is given its name back and nothing takes its place; the new one is then given the name; and only then is the old one removed, and only while it is still that very thing. If the new one cannot be given the name, the old one is given it back and the spare file removed, so all is as it was. When the old one cannot be given its name back, or cannot be removed at the end, it lies whole under its spare name and the red words say which: "the old one is there whole as NAME, and the new one as NAME" or "the old one could not be removed, and is there whole as NAME". **What is left on FTP, and only there.** FTP still has no way to refuse a taken name, so the name is looked at just before each rename, and what another puts under it between that look and the rename is gone over. That can no longer be the thing the person was asked about, which lies under its spare name until the new one has the name; it can only be a file someone else made in that very moment, which is what the line on the Connect card says, and Folders cannot know that it happened. Tested: `a_file_on_a_server_that_is_replaced_is_not_lost_when_the_new_one_cannot_be_named` and `on_a_server_that_cannot_refuse_what_came_in_the_last_moment_is_not_written_over` in `src/files/far.rs`.
      - **Saving back** (15 October 2026): a changed copy of a file opened from a server goes back as a new copy written beside the file under a spare name, checked to be the length it should be, then swapped in by the same step as any other taking of a name (`save_back`, `Hands::name_it`); the old file stays until the new one has the name, and a failure leaves it as it was and says why under "could not be saved on the server".       - **Reading what was named.** One function opens a thing the person or another program named: `common::files::open_named`, used by copies and moves (the toolkit's `src/common/file_work/work`), by what goes to a server (`src/files/far.rs`) and by what is dragged to another program (`toolkit::dnd::portal`). It opens by name alone, which follows no link at its end and never waits; it looks at what it opened; and it answers an ordinary file, a folder or a link, each as the thing itself, kept open, and refuses anything else: a pipe, a device or a socket is never opened to be read, so nothing waits on one. What is then read, listed or handed over is that opened thing and never its name again; what is in a folder is listed from the opened folder and each thing in it opened from that folder. A link is made again as a link by a copy on this computer, is never sent to a server and is never handed to another program as what it leads to (X-1: a folder sent to a server sent each link in it as the file it led to, so a link to a private key put the key on the server; a named pipe in it was opened like a file and the work waited for ever). The one exception is the person's own word: a link they picked themselves and copied to a server is followed, once, to an ordinary file or a folder, and is opened by the same function; a link another program named, or one found inside a folder, never is. Reads have no deadline of their own, as nothing that can wait for ever is opened: a disk or another computer that has stopped answering holds only the thread of the work, never the window's, and a drop is given up after five seconds (`CHECK_WAIT`). **Hidden things are judged as they are read** (F-4): a folder another program named is looked through before the person is asked, to its end and at every depth, and every hidden thing and every link in it is noted; as the folder is then brought, a hidden thing or a link that was not there at the look is left and named, "it was not there when this was looked at, so it was left", whatever the folder held and whatever the person answered. Before, that held only for a folder found to hold nothing hidden, so a project the person had agreed to bring with its `.git` also brought any hidden file put into it after they were asked. A folder too big to look through to its end, which the card says, is brought as it is found. What goes to a server from a drop is held to the same (B-1 of the third review: such a copy was not judged at all).
      - **Handing over.** What was dragged to another program as a move goes to the Trash only when three things are proved. That program read every byte of every send of this drag: every form it asked for, whether it asked while the thing was held over it or after it was let go (X-2: one asked for before the letting go and never read was passed over, so a program could read the list of files, ask for the portal's key, leave it, and still have the originals put in the Trash). The proof is one the kernel can give: a pipe says what lies in it unread, and a send down a pipe is whole when that is nothing. An ordinary file takes whatever is written to it, and a socket reads as emptied once the other end has closed, read or not, so a send down either proves nothing, whatever the program then says (D-1: a program that handed over a file, or one end of a pair of sockets, read nothing and said it had finished a move had the originals put in the Trash). And each thing is still the very thing that was picked up, unchanged (X-3: a file saved again meanwhile is a file the other program never had). With no proof of reading the move is done as a copy: every byte is still sent, nothing here is removed, and the status line says so in red, as the move asked for did not happen: "The other program took what was dragged in a way that cannot show it read all of it, so nothing here was moved: what it has is a copy." A copy that was asked for needs no proof and says nothing. A thing that changed is left and named: "report.txt changed after it was picked up, so it is still where it was." **How the code is held to it:** the Trash step takes `proof::Handed`, which can be made only from the toolkit's proof of a whole hand-over (`dnd::Taken`) and a thing found to be as it was when it was picked up.
      - **Kept logins.** A login Folders holds, in the keyring or in memory, is sent only to an address the person saw on the sign-in card and pressed Open on for that very login, and only within 90 days of doing so. **A computer named by its address is held to the same** (N-2: before, a login kept under "smb://192.168.1.20/" went to that address for ever, with no list looked at, though the address may be another device's by now): the address must be on that login's list, signed in to within the 90 days, or the card asks afresh. A login an earlier file manager kept under an address is so asked for once. **How the code is held to it:** an address is written to a login's list only with `shares::Confirmed`, which only Open on the card makes, from the address that card showed. **An address only heard is asked about every time** (the owner's decision of 13 October 2026 on N-H1 of the fifth review; it reached the builder second-hand and waits for his own word before it is merged). **The fault:** within those 90 days a device that took over the very address a login was signed in to, and answered to the computer's name, was sent that login's exchange with no card. An announcement on a network can be made by anything on it, so for an address that was only heard there is now no memory at all: a login Folders holds, in the keyring or in memory, is never sent to such an address until the sign-in card has shown that address, at this very opening, and the person has pressed Open. Drives are `/media`, `/run/media` and `/mnt`, and any real disk or other computer's folder mounted somewhere else of the person's choosing, never the system's own disk or folders. Ordinary visible files of the home folder and of a drive are copied without a question, as before. What is dragged inside Folders' own windows never comes this way and is unchanged.
        - **The question** is a card over the window, as Folders' other questions are: "Copy id_made_up here?" (or "Copy these 3 items here?"; "Move" when the person holds Shift; "Bring" when the drop is one that asks). Under it: "Another program dropped it on Folders and named it itself. Any program can name any file, and what is named here is not all ordinary files of yours, so nothing is copied until you say." Then what would be brought, a line each, those asked about first with the reason, "id_made_up, from ~/.ssh: hidden, or in a hidden folder" (the other reasons: "has hidden things in it", "has too much in it to look through, so its hidden things are not brought", "outside your home folder and your drives"), six at the most and then "And 4 more."; and where to: "Into Downloads."
        - **A folder too big to look through brings no hidden thing** (15 October 2026, 291a; built 18 October). A dropped folder that cannot be looked through to its end (too many things, too slow, or one in it cannot be read) is asked about as "has too much in it to look through, so its hidden things are not brought", and whatever the answer, the work brings from it no hidden thing and no link at any depth: each that is left is named in the red words as "x (too big to check fully, so it was left)" (`work::TOO_BIG_TO_CHECK`). The ordinary things in it are brought as ever. The same rule holds for a folder of a server (`work::not_there_why`).
        - **Copy is not the answer it starts on.** The one main action, the pill, is "Leave it", and the keyboard starts on the close button, which leaves it too, as Escape does. "Copy it" is the quiet word button at the other end. One answer covers the whole drop.
        - **The program is not named**, because the compositor cannot tell it: the standard way things are dragged between programs on Wayland says nothing of who is dragging, so the card says "Another program". If the compositor is ever taught to say, the card should name it.
        - **The other program waits for the answer.** It is told the drop is finished only once the person says to bring it and the work is done, and told it came to nothing when they leave it or when the card gives way to another. A thing that is no longer the very thing that was looked at by then is not brought (see "What was checked is what is brought"). A second drop while the card is up is turned away: "Answer the question about what was dropped first."
        - **What was checked is what is brought** (12 October 2026, from the second review of that day). **The fault:** each thing was checked once, by its name, when it was dropped, and copied later by opening that name again, following links; the card's answer only looked whether the name was still there. A program could drop an ordinary file beside a hidden decoy, so the card listed the file as ordinary, and put a link to a private file under its name while the card was up. **The rule**, for this and for every copy Folders makes (`work::Which`, `work::open_same`): a thing is opened first, never through a link, what was opened is looked at, and the copy is read from that very opened thing; nothing is checked by a name and then opened by the name again. When it is dropped, each thing is opened without following a link and judged by where the opened thing truly is; which thing it is (its disk and its number on it) is kept with the drop, with the card too. When the work begins, each must still be that very thing, or nothing of the drop is brought: "One item could not be copied: report.txt (it has changed since it was dropped, so nothing was brought)." in red. Inside a folder the same holds all the way down: a folder is opened without following a link and must be the folder that was listed, its items are listed from the opened folder and not from its name, and each file is opened without following a link and must be the file that was listed, else it is among those that could not be copied, "(it changed while it was being copied)". A pipe, a device or a socket is never opened at all.
        - **A link is judged by where it leads, and a folder by what it held when it was looked through** (12 October 2026, from the third review of that day). **The faults:** a link was judged only by where the link itself lay, so a link in Documents to a private key came with no question and left a link to the key where the other program could read; and only the things dropped were held to what was looked at, not what was in them, so a folder looked through and found ordinary was listed again when it was copied, and a hidden thing or a link put into it meanwhile, as while the card was up for something else, came unasked. **The rules:** a link dropped, or anywhere in a folder that is dropped, is also judged by where it leads, every link followed: to something hidden, to somewhere outside the home folder and the drives, or to nowhere (a link that leads nowhere today can be made to lead anywhere), and it is asked about: "invoice, from ~/Documents: a link to something hidden, or outside your home folder and your drives", or for a folder "has a link in it to something hidden, or outside your home folder and your drives". Brought, a link comes as the link it is, never as what it leads to. A folder that cannot be read to its end has not been looked through, and is asked about as one too deep is. And a folder that was looked through and found ordinary is held to that (`work::Sure::clean`, `work::came_since`): the links in it then are noted, and the work brings out of it, however deep, no hidden thing and no link but those; anything else is left and said, "One item could not be copied: .cache (it was not there when this was looked at, so it was left)." Ordinary files put there meanwhile come as ever, as they would have with no question. Each thing dropped is also kept open from when it is looked at until it is brought (the first 256 of a drop; `outside::HELD_MOST`), so its number on the disk cannot be given to something new meanwhile and pass for it. Tested in `src/files/outside.rs`: `a_link_dropped_is_judged_by_where_it_leads_too` and `what_is_put_into_a_dropped_folder_after_it_was_looked_through_is_not_brought`.
        - **A place that does not answer** (12 October 2026). The looking is not done in the window: a folder of another computer that has stopped answering would hold every pane still. It is done on a thread of its own, and the program the drop came from waits as it does for the card. After five seconds with no answer (`outside::CHECK_WAIT`) Folders gives up: "The place report.txt is in is not answering, so nothing was brought." in red, the other program is told it came to nothing, and whatever the looking says later is thrown away. A second drop while one is being looked at is turned away: "The last thing dropped is still being looked at." Folders let go on the Pinned part are looked at the same way before they are pinned, and after a move another program took, which of the originals are still here is looked at off the window too.
        - **What this costs.** A program that hands files over by way of a temporary or hidden folder, as some archive programs and browsers do, is asked about each time, and so is a folder with a hidden folder in it, such as a project with `.git`. That is the price of never copying a private file unasked.
        - **Tested** in `src/files/outside.rs`: `what_another_program_names_from_a_private_place_is_asked_about_first`, `a_move_of_what_is_asked_about_waits_for_the_answer_and_for_the_work`, `which_places_are_private_and_which_are_a_persons_own` and `a_folder_is_not_put_inside_itself_by_another_name`; and `a_folder_sent_into_itself_through_a_link_is_refused` in the toolkit's `src/common/file_work/work`. For the second review: `what_is_put_in_its_place_while_the_card_is_up_is_not_brought` and `a_place_that_does_not_answer_is_given_up_on` in `src/files/outside.rs`; `a_file_is_copied_from_what_was_opened_and_never_through_a_link`, `a_folder_swapped_for_a_link_while_it_is_copied_is_not_gone_into` and `a_folder_the_copy_made_itself_is_said_not_to_be_copied` in the toolkit's `src/common/file_work/work`.
      - **Dragged out of Folders.** Whatever is dragged in a pane, by either button, is offered to other programs as the drag begins, when it is real files and folders of this computer; a server's files and what is inside an archive have no path another program could open, so they stay in Folders. Taken as a copy, nothing changes in Folders. With Shift held as the drag begins they are offered as a move, and when the other program takes that and says it has finished, whatever of them is still there goes to the Trash by the usual work, where Undo brings it back; never before it has finished. Let go on nothing, or on a program that does not want them, or given up with Escape, nothing changes. Inside Folders' own window everything is as it was: the same-drive rule, Ctrl and Shift as it is let go, the right button's menu, the sidebar.
      - **An app of its own still.** None of this needs the ring, Trindle's compositor or any other Trindle program: it is the standard way programs hand each other things, in the toolkit Folders is built on.
    - **Redo** (11 October 2026). Beside Undo in the top bar is Redo, also on Ctrl+Y and Ctrl+Shift+Z, which does again the last thing Undo took back: a move, a copy, a new name or many, the Trash, putting back, a new folder or document, a link, extracting, compressing and everything else Undo covers. Undo and Redo can be pressed back and forth as often as wanted. Doing anything new empties what could be redone, and what is deleted permanently or wiped is forgotten by both. Each button's tip says what it would do, "Undo moving 3 items (Ctrl+Z)", "Redo renaming report.pdf to notes.pdf (Ctrl+Y)", and it is grey, with "Nothing to undo" or "Nothing to redo", when there is nothing. Each keeps the last ten. A text box with the keyboard keeps these keys for its own typing.
      - **How.** Undoing a step answers the step that does it again: a thing moved back is moved there again; a thing Undo put in the Trash (a copy, a new folder, what was extracted) comes back out of it, so a copy is not made twice; a thing Undo took out of the Trash goes back in, to its old place there with its old note; names changed are changed again. So Redo is an undo of the undo, done by the same work with the same care (anything in the way is kept, never written over), and only the part of an undo that was really done is offered again.
    - **Closing the window while work goes on** leaves the work going: the window goes off the screen and Folders stays running. Opening Folders again brings the same window back with the work in its feet. With the window away, work that meets a question, or ends with something it could not do, brings the window back by itself, so neither waits unseen; when all the work is done and nothing went wrong, Folders ends. A window with a question already on it does not close until the question is answered or the work stopped, and says so. Folders does this itself, with its own window, and asks nothing of the ring or any other part of Trindle. Before 11 October closing the window stopped the work.
